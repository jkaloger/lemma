**35. Drift is measured on the symbol.** The re-pin refusal in decision 32 (DELTA-005) compares the receipt's test symbol, not its file. A pin has drifted when the symbol's extracted text at the pin commit differs from its text at HEAD while the claim's text lines did not change (the claim comparison is unchanged: commits between pin and HEAD touching the receipt file, or a working-tree edit). `.rs` and `.ts`/`.tsx` use the lazyspec extractors; a file with no extractor compares whole-file as before. A symbol absent at the pin counts as changed. An agent's own later commits to a `#[cfg(test)]` module, or a doc-comment chore, no longer refuse, so `lemma re-pin <delta>` at review-ready is routine and `--force` is for a changed test under an unchanged claim only. Amends decision 32 (DELTA-005).

**36. Forced re-pins are marked.** `--force` writes ` [forced]` after the sha on the `@ref` line. `lemma validate` warns on every forced receipt of an in-progress delta or a spec: `<claim>: receipt was force re-pinned; review the test against the claim, then remove [forced] or add @checked`. The `in-progress` → `complete` gate and its dry-run report the same warning, so the approving human sees it; the fold carries the marker into the spec. `re-pin` and `lemma receipt` preserve the marker when they rewrite the line. Only a hand edit removes it. Amends decision 32 (DELTA-005).

**37. `lemma receipt` is delta-only and respects drift.** It refuses a document that is not a delta: spec receipts arrive by fold, and humans write `@checked`. When the claim already has a receipt for the same `<path>#<symbol>`, it applies decision 35 and refuses when the pin has drifted, naming `lemma re-pin <delta> <claim-id> --force`. Amends decision 16 (DELTA-002).

**38. Agent-facing commands say what they wrote.** `receipt`, `re-pin` and `base` add `"wrote": [{"id", "part", "line", "text"}]` to their JSON output, one entry per line written or rewritten. Omitted when empty; hook commands unchanged.

**39. Missing receipt on in-progress is a warning.** `lemma validate` reports `claim has no receipt` on an in-progress delta as a warning. The `complete` gate keeps it an error. The in-progress window is the only one the agent works in; an error there makes CI red on every push of a feature branch and trains agents to ignore exit 2. The CI template comment says so. Amends decision 31 (DELTA-005).

**40. Overlap counts drafts.** "Two in-flight deltas touching one claim id" counts `draft` and `in-progress`, the sense of in-flight the `@base` paragraph (decision 34, DELTA-005) uses, so the collision is reported while it is cheap. Amends decision 31 (DELTA-005).

**41. Dry-run names uncommitted delta files.** The by-hand `in-progress` check adds a warning per uncommitted file of the delta bundle: `<file> has uncommitted changes; commit the delta before asking for review`. A warning, not an error, because the real transition itself edits `index.md`. `checked … ready` still follows when there is no error. Amends decision 14 (DELTA-001).

**42. Stop diffs against the session base.** The plugin gains a `SessionStart` hook running `lemma session-start`, which reads `session_id` and `cwd` from stdin and writes HEAD's sha to `<git-dir>/lemma/sessions/<session_id>` unless the file exists (a resume keeps the original base). `lemma stop` reads the file for its `session_id`; touched files are the union of `git diff --name-only <base> HEAD`, tracked working-tree changes and untracked files. With no base file it diffs against HEAD as before. The "complete in the working tree but not at HEAD" check keeps comparing against HEAD: a human who completes and commits mid-session must not be flagged on every later Stop, so decision 24's (DELTA-004) "commit inside the session escapes" note stands. A delta that became `complete` since the base counts as covering its specs in the cross-`governs` check. Amends decision 5 (DELTA-001).

**43. Spec activation.** `draft` means the Intent is proposed and no fold has been accepted; `active` means the spec describes real behaviour. A human moves it; nothing automatic. The `in-progress` → `complete` gate and its dry-run warn for each draft target: `<spec> is draft; move it to active once this fold lands`. README defines both states. Amends decision 3 (DELTA-001).
