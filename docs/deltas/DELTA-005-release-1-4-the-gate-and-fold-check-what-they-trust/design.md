In: clean tree at `complete`, fold base check, validate error severities, per-claim re-pin, test-path receipts, README ordering and trust model. Test execution is out: receipts stay symbol resolution and the trust model is stated, not changed.

**29. Clean tree at `complete`.** The `in-progress`→`complete` gate errors when any receipt file or any file under a target's `governs` has uncommitted changes (`git status --porcelain` on those paths). Same rule `lemma receipt` applies in decision 16 (DELTA-002): the working tree the symbols resolved against must be the commit the pin names. Amends decision 5's "Stop concern" split (DELTA-001): Stop still owns ungoverned drift.

**30. Fold checks the base.** A delta claim that replaces or strikes a spec claim carries `@base <hash>`, the hash of the spec claim's block (text and receipts, not the id line's indentation) at the time the delta claim was written. `lemma receipt` and the delta skill write it; `draft`→`in-progress` errors on a replace or strike without one. The fold errors when the spec's current block hash differs from `@base`, naming both. A delta claim whose id already exists in the spec and has no `@base` is an error, so an accidental id collision cannot overwrite. Replaces the "two in-flight deltas touching one claim id" warning, which stays as a warning. Amends decision 7 (DELTA-001) and 20 (DELTA-003).

**31. Validate severities.** Invariants are errors; drift is a warning. Errors: claim without receipt on an in-progress delta; receipt does not resolve; fold target does not resolve; part/target mismatch (decision 19, DELTA-003); claim in `index.md` (decision 18, DELTA-003); replace without `@base`. Warnings: receipt stale; `@base` mismatch on a draft; intent count; two in-flight deltas on one id. The CI template keeps `lazyspec validate --warnings` and now fails on the error set. Amends decision 13's note (DELTA-002): drift is advisory per RFC-001 §7.7 (DECISION-009), invariants are not.

**32. re-pin per claim.** `lemma re-pin <id> [claim-id ...]` re-pins the named claims, or every claim when none are named. Decision 9's flag (DELTA-001) becomes a refusal: a receipt whose file changed between the old sha and HEAD while that claim's block is unchanged is not re-pinned (exit 2, nothing written) unless `--force` is passed, which writes and emits the warning. The comparison is per claim: a receipt file change counts as reviewed when the claim's text lines (block minus `@ref`, `@checked` and `@base` lines) changed in a commit that also touched the receipt file, or are edited in the working tree. A receipt file with uncommitted changes is refused outright, `--force` or not. Amends decision 9 (DELTA-001) and 23 (DELTA-003).

**33. Receipts name tests.** `@ref` paths must match the governing spec's `tests` glob list, a new frontmatter key beside `governs` (default: `**/tests/**`, `**/*_test.*`, `**/*.test.*`, `**/*.spec.*`). A production symbol is not a receipt. `lemma receipt` refuses, validate and the gate error. README states the trust model in one paragraph: a receipt is a resolving symbol in a test file at a commit, not evidence the test ran or passed; the project's runner and the human reviewer own those.

**34. `lemma base <delta> [claim-id ...]`.** Decision 30 has the skill write `@base`, but an agent cannot compute a hash by hand, so a subcommand does it. For each named claim, or every claim whose id exists in its target spec when none are named, it writes `@base <hash>` as an indented line under the claim from the spec's current `behaviour` block, replacing an existing `@base`. It refuses (exit 2, nothing written) on an unknown claim id, a claim whose id the target spec lacks, or an unresolved target. `lemma receipt` inserts `@base` only when the claim's id exists in the spec and no `@base` is present. The hash is the first 12 hex chars of SHA-256 over the spec claim's block: each line right-trimmed, the id line left-trimmed, `@base` lines excluded, joined by `\n`. The fold strips `@base` lines from a claim before writing it into the spec. A struck claim whose id the spec lacks is an error at `draft`→`in-progress` and in validate. A claim carrying `@base` whose id the spec lacks is drift: a validate warning, a fold error.
